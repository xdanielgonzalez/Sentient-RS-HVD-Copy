01High-priority writeups

MinIO write-through mirror (start / stop-sweep)

COMPOSITE ACTION

The most duplicated non-trivial block in the repo. Two steps travel together every time: a Start MinIO mirror write-through step that backgrounds mc mirror --watch per prefix (writing PIDs to /tmp/mc-watch.pids, disowning so it survives the step), and a paired if: always() stop-and-final-sweep step that kills those PIDs, tails the watcher logs, and does one more mc mirror --overwrite --quiet pass.

Occurrences
_yocto.yml:119–162 (start) / _yocto.yml:235–270 (stop)
production.yml:501–526 (start) / production.yml:627–656 (stop)
Drift
Real and dangerous. _yocto.yml's start step carries extra diagnostics production.yml's copy lacks: a captured mc alias set error message (err="$(...)" showing key_set/secret_set booleans), an explicit mc ls --recursive --summarize read-side probe, and an explicit mc anonymous get policy check. These diagnostics were added to _yocto.yml specifically to debug the "Mirrors=294, cold" gotcha noted in project memory (yocto-image-green-mirror) — production.yml's copy will hit the same failure mode blind, with only a generic mc alias set failed warning to go on.
Inputs
minio-access-key, minio-secret-key (secrets, passed explicitly — composite actions cannot read secrets.* implicitly), cache-root (default /opt/yocto-cache), prefixes (default sstate downloads)
Outputs
none required; could emit pids-file path for symmetry with a separate stop action, or fold start+stop into one action with a mode: start|stop input
Gotchas
The background mc mirror --watch process must survive the step boundary (nohup + disown) — a composite action's steps run in the same shell process tree as the calling job, so this should still work, but verify disowned children survive a composite action step boundary specifically (not just a plain workflow step) before relying on it. The stop step must run if: always() at the call site — a composite action step cannot force its own if: condition on the caller, so the workflow author must still remember to gate the stop invocation with if: always().

openssl X.509 CMS sign + verify

COMPOSITE ACTION

Five near-identical sign blocks, each: write SIGNING_KEY/SIGNING_CRT/CA_CRT to mktemp files with a shred -u trap, openssl cms -sign, then a three-way verify degrade — CA-chained verify passes clean, a self-signed cert falls back to -noverify with a warning, an actually-broken signature hard-fails.

Occurrences
_yocto.yml:356–386 (golden bundle) · _yocto.yml:480–514 (shipping .wic) · production.yml:80–123 (validate-signing preflight, throwaway blob) · production.yml:692–727 (app sysext .raw) · production.yml:841–882 (RPi binaries, loop over multiple files)
Drift
Low on the core sign/verify logic (all five copies use the identical three-way degrade), but the surrounding shape differs: the RPi-binaries copy loops over a glob with a case exclusion list, the app-sysext and .wic copies loop over a smaller glob, and the validate-signing copy signs a /dev/urandom throwaway and exposes a tier output instead of writing a .p7s file. A composite action needs a mode or a glob-pattern input to cover all five without re-forking the copy-paste.
Inputs
signing-key, signing-crt, ca-crt (secrets, explicit) · target-glob (files to sign, e.g. dist/bin-rpi-*) · exclude-suffixes (optional, for the RPi-binaries case) · throwaway (bool, for the validate-signing preflight variant)
Outputs
tier (release / prerelease / unset-on-skip) · signed (bool) — every call site currently re-derives its own notion of "did signing happen" from the same [ -z ... ] && exit 0 guard; a shared output normalizes this
Blast radius / risk
5 call sites across 2 files, all release-critical (a broken extraction breaks shipping). Secrets must be passed as explicit composite-action inputs — secrets.SIGNING_KEY is not visible inside a composite action body. Every copy already writes key material through mktemp with a trap ... EXIT shred — preserve that exactly; a composite action step's trap scope needs verifying (does it span only that step, or the whole composite invocation?).

cgroup-aware BitBake parallelism

SHARED SCRIPT — .ci/scripts/bitbake-parallelism.sh

Reads /sys/fs/cgroup/cpu.max (falls back to nproc) to get the real CPU quota GitHub's cgroup-blind sched_getaffinity can't see, then generates a kas local_conf_header YAML fragment pinning BB_NUMBER_THREADS/PARALLEL_MAKE.

Occurrences
_yocto.yml:174–204 (build-image job) · production.yml:601–612 (sysext job)
Drift
The two copies are functionally different, not just textually. _yocto.yml also reads /sys/fs/cgroup/memory.max and caps the thread count by RAM (JMEM = MEMGB / 4, then J = min(N, JMEM)) — added specifically because a CPU-only cap was still OOM-killing cold builds at ~95 minutes (see the inline comment referencing "MEMORY-CAPPED parallelism (reverts the earlier MAX PROCS directive)"). production.yml's sysext job still uses the old CPU-only formula that _yocto.yml explicitly moved away from. This is a real, live bug risk: the sysext job builds on the same ARC pool with the same OOM history, and nothing informed it of the fix.
Recommended form
A checked-in script, not a composite action — this is pure computation with no secrets and no side effects beyond writing a file, matching the existing convention (junit_to_summary.py, robot_output_to_summary.py). Script writes the kas fragment path to stdout or $GITHUB_OUTPUT; callers do PARCONF="$(.ci/scripts/bitbake-parallelism.sh)".
Priority driver
High not because of line count (it's short) but because the drift is an active regression in production.yml's sysext job — extracting this fixes a latent OOM risk as a side effect, not just a style cleanup.

02Medium / low priority — brief notes

kas build harness (mkdir + chown + runuser -u builder)

The mkdir -p "$KAS_WORK_DIR" / chown -R builder:builder ... / runuser -u builder -- env HOME=/home/builder KAS_MACHINE=... kas {shell,build} ... shape repeats at _yocto.yml:206–214, production.yml:613–621, uat.yml:133–138, and uat.yml:290–296. Drift is mostly cosmetic (which env vars get forwarded, kas build vs kas shell -c), but the root-container-then-drop-to-builder dance is a real gotcha worth centralizing in one place with a comment, rather than four. A composite action works if it accepts the kas subcommand (build / shell -c "...") as a parameter; otherwise a documented shell function in a sourced script is lower-risk given runuser's privilege-drop semantics are easy to get subtly wrong in a generic wrapper.

checkout + Setup composite pairing

Every job that touches Rust starts with actions/checkout@... (almost always submodules: recursive) immediately followed by uses: ./.github/actions/setup with the same three inputs. ~16 call sites. This is already about as DRY as GitHub Actions allows short of a reusable-workflow-per-job (which would fight the current "reusable workflow per concern, composite action per tool setup" shape that's working well). Not worth a new abstraction; if anything, consider adding submodules: recursive as a fixed default baked into the checkout usage via a thin wrapper composite (.github/actions/checkout-setup = checkout + setup in one), saving one step per job — cosmetic, low value.

MinIO golden-image pull (mc stat / mc cp against golden store)

uat.yml (uat.yml:163–181, pulling the qemuarm64 tarball) and production.yml's sysext job (production.yml:537–566, pulling the shipping .wic) both do: mc alias set → mc stat a fixed golden key → mc cp the object + its .p7s sidecar → error loudly if missing. Already drifted: uat.yml assumes a single fixed extension (.tar.gz), production.yml's copy loops over wic.bz2 then wic tolerantly. A shared script (.ci/scripts/mc-pull-golden.sh <machine> <ext-list> <dest-dir>) unifies both without forcing a composite-action secrets dance for what's a two-line curl-equivalent.

Digest-pinned builder-image container refs

~14 container: 10.0.0.246/sentient/sentient-*-builder@sha256:... lines across 8 workflow files. This duplication is real but already has a purpose-built fix: .ci/update-build-sha.sh mechanically rewrites every one of these refs (its own BASE_WORKFLOWS / WORKFLOWS arrays list exactly the files to touch) and has a --check mode for a drift gate. The actual gap isn't the duplication — it's that nothing in _supply-chain.yml's zizmor/audit job currently runs update-build-sha.sh --check as a CI gate, so a stale digest can land and merge silently. Recommendation: wire the existing script into a check, don't build a new abstraction. A YAML anchor or reusable env: block can't cross separate workflow files in GitHub Actions, so there's no native way to fully eliminate the repetition short of this kind of generation script, which already exists.

Pre-release tag computation (date.run_id)

Computed once in _yocto.yml's qemuarm64 leg (_yocto.yml:330–348, steps.prerel.outputs.tag) and recomputed in the same file's shipping-machine leg (_yocto.yml:576–582, steps.prerel_tag.outputs.tag) because matrix legs are separate jobs that can't share step outputs. The inline comment already acknowledges the UTC-midnight double-tag edge case and accepts it. This is a matrix-parallelism constraint, not a copy-paste smell — extracting it to a script wouldn't remove the duplication (each leg would still need to invoke the script independently); the real fix would be promoting the tag computation to a workflow-level outputs: on a tiny prerequisite job the matrix needs:, which is a job-graph change, not a reusable-form extraction. Low priority, flagged for completeness.

docker/setup-buildx-action Harbor-trust block

builder-image.yml's base and derived jobs (builder-image.yml:54–71 and builder-image.yml:128–137) repeat the identical buildkitd-flags: --allow-insecure-entitlement network.host + driver-opts: env.SSL_CERT_DIR=... + buildkitd-config-inline: [registry."10.0.0.246"] ca = [...] block, plus an identical "Write Harbor robot creds to docker config" step. Confined to one file, two jobs — a composite action would help if a third builder-image job is added later, but two occurrences in one file is thin justification today.

03Other duplication worth flagging

  • Env-var-not-interpolation pattern. Every run: block that touches a ${{ github.* }} or ${{ inputs.* }} value correctly routes it through env: first (zizmor template-injection avoidance) — this is consistently applied, not a smell, but worth calling out as a convention worth codifying in a repo-level zizmor rule comment or a CONTRIBUTING note so new workflow authors don't reintroduce direct interpolation.
  • if-no-files-found: error convention. Consistently applied on artifact uploads that must not silently no-op (test-e2e junit, Renode results). Good, no action needed — noting it as a pattern worth preserving when extracting the upload step elsewhere.
  • Concurrency-group naming. Every workflow sets concurrency: group: <name>-${{ github.ref }} with a workflow-specific cancel policy (ci.yml cancels, uat.yml/image.yml/production.yml don't). Not duplicated logic, just a repeated shape — fine as-is, each choice is deliberate per the inline comments.
  • permissions: blocks. Each reusable workflow declares its own minimal permissions: contents: read (occasionally write for release jobs). Correctly scoped per job already, not a duplication problem.

04Suggested sequencing

Ordered for maximum smell reduction per unit of risk — cheapest, highest-confidence wins first; the two release-critical composite actions (signing, MinIO mirror) come after the scripted fix that needs no new abstraction at all.

Wire update-build-sha.sh --check into _supply-chain.yml Zero new code — the drift-detection script already exists. Closes the digest-pin gap immediately and is a template for how "already-scripted" duplication should be gated going forward.
Extract cgroup-aware BitBake parallelism to .ci/scripts/bitbake-parallelism.sh Fixes the live OOM-risk drift in production.yml's sysext job as a side effect of the extraction — this is a bug fix wearing a refactor's clothes. Pure computation, no secrets, lowest risk of the composite-action candidates.
Build the .github/actions/cms-sign composite action Five call sites, release-critical. Do this before touching the MinIO mirror action so the two land independently and each gets its own focused review — signing correctness is the higher- stakes of the two.
Build the .github/actions/minio-mirror composite action Port _yocto.yml's more complete diagnostics (the captured alias-set error, the read-side probe) into the shared action so production.yml's sysext job inherits them — this extraction is also a bug-parity fix, not just deduplication.
Shared script for MinIO golden-image pull, then the kas-build-harness composite Lower urgency; do these once the release-critical extractions have proven the composite- action pattern works cleanly against this repo's ARC/runuser environment.
Every composite-action candidate above needs secrets passed as explicit inputs: — composite actions cannot read secrets.* the way reusable workflows can with secrets: inherit. Each call site will need a small mechanical change (minio-access-key: ${{ secrets.CACHE_AWS_KEY }} etc.) alongside the extraction itself; this is not optional plumbing, it's how GitHub Actions scopes secret access to composite actions.
